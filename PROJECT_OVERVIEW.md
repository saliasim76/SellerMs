# SellerMS — Project Overview

*Audit performed 2026-08-28. Read-only investigation: code reading, a locally-booted instance on port 5050, curl against live routes, and read-only SELECT queries against the real local MySQL database. No files were changed, no data was written/deleted, nothing was deployed.*

---

## 1. Executive summary

SellerMS is a single-codebase Flask/SQLAlchemy ERP for a trading/distribution business (Purchase, Sales, Chart of Accounts, Journal/GL, Employees, Payroll), with a second, mostly-separate SaaS layer bolted on top that can provision the same ERP schema into a dedicated MySQL database per paying customer, plus a merged-in marketing/trial-signup site ("Proledg"). It is a real, actively-developed local project — not a toy: the database already holds real day-to-day activity (68 employees, live Chart-of-Accounts entries created today, a genuine multi-hour server log with almost no errors) — but it has never been deployed anywhere; there is no server config, Docker, or CI of any kind. The single biggest risk found is architectural, not cosmetic: the custom Role & Permission system is real and well-built, but its enforcement decorator is only actually used in 5 of the app's ~35 route modules — meaning any logged-in user, of any role, can create/edit/delete/GL-post Purchase and Sales documents (the two largest modules, ~210 routes combined) regardless of what their assigned role permits. A second, fully-reproduced bug crashes with a raw 500 error for any anonymous (logged-out) visitor who hits a bad URL. Someone picking this back up should treat RBAC enforcement in Purchase/Sales as the top priority before this goes anywhere near real users.

## 2. What the site actually does

Verified by reading the route/template code and exercising it live:

- **Core ERP** for a single business: Owners/Sellers, Buyers, Suppliers (banks, documents, departments), Employees (professions, allowances, banks, documents, work allocation history), Payroll (monthly generation/lifecycle), Purchase (Request → Quotation → Order → Goods Receipt Note → Invoice → Goods Return Request → Return Note → Debit Memo), Sales (mirror image: Quotation/Order → Delivery Note → Invoice → Return Request → Return Note → Credit Memo), a 5-level Chart of Accounts, a Journal/GL ("GRL") posting system, separate Purchase/Sales Tax Codes, Stores (Fixed Asset / Consumable / Non-Consumable) with stock transactions, an Excel import/export tool for master pages, a Recycle Bin (soft-delete with 7-day auto-purge), an Audit Log, and a database Backup/Restore admin tool (raw pymysql dump/restore to/from JSON).
- **RBAC**: a role/permission-matrix engine (Modules → Forms → Actions, e.g. `purchase.purchase_order.approve`) with a `SuperAdmin` seed account, `is_super_admin` flag, per-role and per-user permission overrides, and a UI to manage it — see section 5/6 for how much of it is actually enforced.
- **2FA**: TOTP-based two-factor login (`pyotp` + QR code) is real and wired into the login flow.
- **Bilingual UI**: English + Arabic (RTL) is real and pervasive; the code also has scaffolding for French/Urdu/Hindi/Bengali as a configurable "second language," gated behind a single Owner-record setting.
- **SaaS layer**: a Super-Admin module/pricing catalog, a paying-customer onboarding flow that provisions a **real, separate physical MySQL database** per customer with the full ERP schema pre-seeded (verified — see section 5), and a public marketing site (Proledg: home/features/modules/pricing/security/contact/trial-signup) merged into the same Flask process.
- **Ad-hoc free-tier machine translation**: an in-app "Translate" button calls Google's unofficial `translate.googleapis.com/translate_a/single` endpoint and falls back to MyMemory's free API — no API key, no official Google Cloud Translate account (see section 10).

## 4. Architecture

- **Single Flask app, one process** (`app.py: create_app()`), ~35 blueprints registered covering ERP modules, RBAC admin screens, the SaaS admin/customer screens, and the merged-in Proledg marketing site. Blueprints live under `database/routes/*.py`; `models.py` (4,509 lines) holds every SQLAlchemy model for both the ERP schema and the SaaS/control-plane schema.
- **Config** (`config.py`): a single MySQL connection string built from `DB_HOST/PORT/NAME/USER/PASSWORD` env vars (all defaulted if unset), used for **both** the default SQLAlchemy bind and a second `'saas'` bind that, per an explicit comment in `config.py`, points at the exact same database — the `'saas'` bind key is now just a way for the code to tell "control-plane table" apart from "tenant business table" logically, after an earlier "Phase 4" migration merged what used to be two physical databases into one.
- **Multi-tenancy mechanism** (`database/tenant_routing.py` + `database/tenant_provisioning.py`): a custom `TenantAwareSession` subclass overrides SQLAlchemy's `get_bind()` so that, once `flask.session['tenant_db']` is set at login (for a user found in `SaasUserDirectory` rather than the shared `users` table), every default-bind query for that request is silently redirected to a per-customer MySQL database (`customer_NNNNNN`), keyed off a small in-process engine cache. Real evidence this works: a genuine orphaned tenant database `customer_000034` exists on the MySQL server with 82 tables and a real renamed admin user inside it, even though the parent row in `saas_customers` no longer exists in the current `sellerms` database (0 rows) — i.e. it was provisioned and later the catalog was reset/cleared, leaving the artifact behind.
- **Trial signups vs. paid customers are architecturally different**: the public "Start Trial" flow (`proledg_site.py` → `saas_internal.provision_trial_user_direct`) just creates a normal `User` row in the **shared** database — trial users do **not** get their own isolated database. Only the Super-Admin-driven "add customer" flow (`saas_customers.py` → `tenant_provisioning.provision_tenant`) creates a real, separate physical database. This is a meaningful, undocumented distinction for anyone reasoning about tenant data isolation.
- **Folder structure that matters**: `database/routes/` (all blueprints + the RBAC engine + tenant/SaaS logic), `models.py` (all models, all seed functions, `ensure_schema()`), `forms.py` (WTForms), `templates/` (one subfolder per module; `templates/proledg/` and `static/proledg/` are the merged-in marketing site, deliberately isolated by filename to avoid colliding with the ERP's own `base.html`/`style.css`), `uploads/` (per-record file attachments, git-ignored in effect but currently full of real committed files being removed in the working tree — see §12).
- **Scheduler**: an in-process APScheduler background thread (guarded against Flask's debug-reloader double-start) runs two daily jobs: recycle-bin purge and auto-pending of expired Purchase/Sales Quotations.

## 6. What's broken

- ❌ **Anonymous users get a raw 500 error instead of a 404 page, on any bad/unknown URL.** Fully reproduced with a traceback:
  ```
  jinja2.exceptions.UndefinedError: 'flask_login.mixins.AnonymousUserMixin object' has no attribute 'is_admin'
    File "d:\Project\SellerMs\templates\base.html", line 535, in block 'body'
      {% if can_admin_users or can_admin_roles or can_admin_recycle or can_admin_audit or current_user.is_admin() or current_user.is_super_admin %}
  ```
  `templates/errors/404.html` extends `base.html`, whose admin-menu block unconditionally calls `current_user.is_admin()`. Flask-Login's `AnonymousUserMixin` has no such method, so it crashes. Confirmed differential behavior on the live server: the exact same bad URL returns `404` when requested with a valid session cookie, and `500` when requested with none. This will hit **every logged-out visitor** who mistypes a URL, follows a stale link, or gets probed by a bot — currently the custom 404/403 pages effectively only work for logged-in users. (`templates/errors/403.html` shares the same `base.html` and is almost certainly affected identically, though not separately triggered live.)
- ❌ **The Role & Permission Matrix is not enforced for the two largest modules (Purchase and Sales), or for most of the rest of the app.** `permission_required`/`permission_required_json` (the actual enforcement decorators in `database/routes/rbac.py`) are used in only 5 of ~35 route files: `audit_log_ui.py`, `rbac.py` itself, `recycle_bin.py`, `role_permission_matrix.py`, `user_management.py`. Every other module — including `purchase.py` (125 routes) and `sales.py` (88 routes), the app's biggest and most financially consequential surface — has **zero** authorization beyond `@login_required` (verified: `grep -c "permission\|is_admin\|role =="` returns 0 hits in both files). Concretely: any authenticated user, regardless of assigned role or explicit permission denial in the Roles & Permissions screen, can create, edit, delete, and **Post & Save** (the GL/stock-mutating action per this codebase's own convention) any Purchase or Sales document. A coarser `is_admin()`-based (`admin` vs `staff` role) check exists in some modules (`coa.py`, `employees.py`, `sellers.py`, `banks.py`, `work_allocations.py`, `db_backup.py`) but is entirely absent from `purchase.py`, `sales.py`, `buyers.py`, `financial.py`, `journal.py`, `grl.py`, `payroll.py`, `unit_measurement.py`, both tax-code modules, `items.py`, `allowance_types.py`, `allowances.py`, and `professions.py`.
- ⚠️ **This directly contradicts the codebase's own comment.** `database/routes/rbac.py` line 47 states: *"Only 'employee_master' and 'purchase_order' are actually enforced by a route decorator this phase"* — but neither `employees.py` nor `purchase.py` contains any call to `permission_required`, `user_has_permission`, or any equivalent check. The comment appears to describe an intended/earlier state that was never implemented (or was later removed) for these two forms. Per the audit brief's "code beats docs" rule, the code — not this comment — is the fact.
- ⚠️ **README claims "ORM-only queries (no raw SQL)"** (README.md lines 31 and 279) — false as written. `database/routes/db_backup.py` runs a full raw-`pymysql` dump/restore (including `DROP`/`CREATE TABLE` and `KILL <connection>` statements); `models.py`'s `ensure_schema()` and `app.py`'s `init_db()` both run raw `text()` `ALTER TABLE`/`UPDATE` SQL for schema/tax-code fixups. None of these are user-input-driven (so not an active injection vector as far as could be determined), but the README's blanket claim is not accurate.
- 🚧 No automated tests exist anywhere in the repository (no `pytest`, no `unittest`, no `tests/` folder).

## 7. What's hardcoded / faked

- The **contact form** on the merged-in marketing site (`proledg_site.py`, `/contact`) doesn't send an email or hit a CRM — it just does `print(f'[contact form] {name} <{email}> — ...')` to stdout. Explicitly marked in the code: `# Placeholder: wire this up to an email/CRM integration later.`
- **No payment processing exists at all**, despite dedicated `saas_payments`/`proledge_saas_payments` table with `payment_status`/`transaction_reference` columns. There's no Stripe/PayPal SDK, no checkout route, no webhook handler anywhere. Trial signups get a real 14-day trial with `total_amount=0` and no card requested; there is no code path by which a customer's subscription ever actually gets billed or a `Payment` row ever gets created.
- **Trial-signup temp password is shown directly on the success page** (`trial_success.html` receives `temp_password` in plaintext) rather than emailed, which is a direct, if implicit, consequence of there being no email service wired up at all in this app.
- **`SuperAdmin` seed password is hardcoded in source** (`database/routes/rbac.py`): `SUPER_ADMIN_PASSWORD = ****` (set, matches the app's default MySQL password value exactly — looks like a real personal password reused as a code default, not a placeholder). Same value is also the default `DB_PASSWORD` fallback in `config.py` and is documented in plaintext in the README's "Quick Start" section.
- **Default `SECRET_KEY` fallback** in `config.py`: `'seller-ms-secret-key-2024-change-in-production'` — used as-is unless the `SECRET_KEY` env var is set, which it is not in this environment (see §10).
- **(Historical, resolved 2026-08-31)** Early in the project, "AG-Grid"/"MUI Grid" naming was cosmetic — no real library was loaded, just a hand-built vanilla-JS grid styled to resemble them, plus a genuine (now-removed) MUI X Data Grid + React implementation on the Employee and Payroll pages, and a dead, unreferenced `templates/payroll/mui_grid.html`. All of that has since been replaced: every grid page now runs on the real AG-Grid library (Community/Enterprise, loaded from CDN), the MUI/React pages were rebuilt on AG-Grid, and the dead file plus its supporting `static/js/mui-grid-persist.js` were deleted. No React or MUI reference remains anywhere in the codebase.
- **Chart-of-Accounts auto-seeding is explicitly disabled** — the code for it is still present in `models.py` but the call site in `app.py`'s `init_db()` is commented out with the note: *"Levels 1-5 were deliberately cleared and must be built manually from here on."* All current COA data in the live DB was entered by hand, not seeded.
- **A stray, unreferenced file**: `templates/deepseek_html_20260823_36b781.html` (an AI-generated tax-invoice mockup, filename pattern consistent with a pasted DeepSeek chat output) sits directly in `templates/`, not `extends`-ed or `render_template()`-ed from anywhere in the Python code — dead leftover, not part of any real flow.
- **Purchase/Sales tax-rate resolution** (`sales.py`) falls back through three layers before giving up: a real `PurchaseTaxCode`/`SalesTaxCode` DB lookup, then a hardcoded `LEGACY_TAX_CODES` dict (`VAT15`/`VAT0`/`EXEMPT`), then a regex-extract of a literal `"15%"`-style string carried over from another document line. Not fake data per se, but a sign the tax-code model went through at least one earlier, less-structured iteration that's still load-bearing.

## 8. Live vs. local-only

- **Nothing is deployed anywhere.** No Dockerfile, no `docker-compose.yml`, no CI/CD config (`.github/` is empty of workflow files), no `Procfile`, no reverse-proxy/WSGI config, no hosting provider references in code or docs. This is a 100% localhost, pre-deployment project.
- The app currently only runs via `python app.py` (Werkzeug's built-in dev server, which prints its own `WARNING: This is a development server. Do not use it in a production deployment.`).
- The live local MySQL database (`sellerms`, on `localhost:3306`) has real, non-trivial data from actual use: 68 employees, real COA entries created earlier the same day this audit ran, and a genuine multi-hour server access log with almost no errors. Purchase and Sales tables, however, are **completely empty (0 rows)** in every document table checked (`purchase_requests`, `purchase_orders`, `sales_orders`, `sales_invoices`) — the two flagship transactional modules, despite being fully built, have apparently never been used to create a single real document yet.
- The SaaS layer's own control tables are effectively empty right now (`saas_customers`: 0 rows, `saas_user_directory`: 0 rows) even though one orphaned tenant database (`customer_000034`) proves the provisioning flow was exercised at some point and then the parent customer record was removed/reset without cleaning up the tenant database it created.
